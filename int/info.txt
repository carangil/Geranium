I've been working on a strongly typed postfix language.  It is inspired by FORTH, but carries over many ideas from other languages.  
It has 2 stacks:  

    The call stack: This keeps track of where the program is, and is also temporary memory for local arrays, structs, named local variables, exist here.  This is like the C stack.
    Eval stack:  The 'classic' FORTH stack that holds temporary values for computation in progress.  10 5 + , etc
    


Basic data types:
    Z32:    32-bit Integer
    N32:    32-bit Unsigned
    N8:     8-bit Unsigned
    String: UTF-8 formatted string.  Guaranteed to always be null terminated.  Index are byte positions, NOT whole characters.
    Real:   Floating point number (currently 32-bit... I might change to 64)
    Pointers, Arrays, Structs


Examples:

    "Hello World" print newline //prints Hello World


    10 5 + print        //prints 15

    10.0 3.0 / print    //prints 3.33333


Converting values

    10:Real 3.0 / print   //prints 3.3333   :Real converts int to float

    "A":N8 //value is 65.  Converting a string to a byte takes the value of the first byte
    


Creating variables w/ assignment

    10 #x       //x is initialized to 10.  Default Z32
    10:N32  #x  //x is initialized to unsigned 10
    10.0    #x  //X is initialized to Real 10.0
    "A":N8  #x  //x is initialized to 65
    
    10 ##x print    //x is initialized to 10... but also left on the stack.  So, this also prints 10

Creating empty variables:

    var i:Z32;  //32-bit integer


Assigning to existing variables:

    10 x =      //To write to a variable, use the variable's name, followed by =
    20.0 y =


Using variable contents

    x print //Using the name of a variable w/out a following = (and other tokens) puts the variable's VALUE on the stack.  This is different from FORTH

    x y + print //print the sum of x and y

    x 1 + x =   //add 1 to x


Using pointers:

    x&  //Pointer to x.  If x as a Z32, then this value is a Z32&
    x& #to_x    //to_x is a Z32& variable, pointing to x
    
    to_x    //this value is a pointer to x
    to_x@   //this derefereces x; returns the contents of x
    5 to_x@=  //writes 5 to x


Creating Arrays:

    [Z32] 10 new    #myArray    //myArray owns an array of 10 integers  Note: inside brackets is the Type of the element!
    [Real] n new    #myArray    //myArray owns an array of n Real numbers
    [N8] 10 new     #myArray    //myArray owns an array of 10 bytes.  An extra byte is always allocated at the end and always contains a null character.  Any [N8] array can be used safely as a string.  N8 arrays can contain null characters, but any procedures expecting a String will top reading at the first null.

Indexing arrays:     

    myArray 0[]     //contents of first (0th) element
    myArray 0[]&    //pointer to 0th element
10  myArray 0[]=    //assign 10 to the 0th element
10  myArray i[]=    //assign 10 to the ith element

Creating Struct Types

type LabeledNumber
    number:Z32;
    label:String%;  //Not a String, but a String%.  % is a type of pointer.
end

Creating an instance of a struct

LabeledNumber new #ln   //ln owns a LabeledNumber.  The datatype of the ln variable is LabeledNumber%. 'new' does a heap allocation.

ln  //address of the struct
ln& //address of ln (the variable holding a pointer to the struct.  This is of type LabelseNumber%&)

ln .numner      //value of the number field
ln .number&     //pointer to the number field
10 ln .number=  //assign to the number field


var myLN:LabeledNumber; //the variable is a LabeledNumber created on the local stack

myLN        //Address of the LabeledNumber on the stack
myLN&       //not allowed; there is no variable holding a pointer to the struct; the struct is just on the stack itself
myLN.number //value of number field
10 myLN.number=     //assign to the number field
myLN.number&    //pointer to the number field

Note, here there is no myLN& ... the is no variable holding a pointer to the struct.

Note, that if someLN is either a struct on the stack, OR is a variable containing a pointer to a struct, then someLN is always a pointer to a struct, and someLN.member is a member. 


Creating an array of structs:

[LabeledNumber] 10 new #myNumbers   //array of 10 structs. 


var ln:[LabeledNumber]%;    //pointer to array of LabeledNumbers.  
ln n[]& //pointer to nth element (pointer to a struct)
ln n[].label    //nth element label field (which is a String%   ... pointer to a String)
ln n[].label&    //pointer to nth label field (  pointer to a pointer to a String...  String%&  ...Wait some pointers are & and some are %... more on that later)


[LabeledNumber%] n new pln=   //create array of n LabeledNumber pointers

pln n[]&  nth pointer to a ln
pln n[].label    //value of label field of nth ln pointer
pln n[].label&   //pointer to label field of nth ln pointer

Note: if you refactor code from Array of pointers to structs to Array of Structs, the code to access the elements and their fields looks the same.


Types of pointers:

There are two types of pointers, Possessive, denoted with %, and Reference, denoted with &.

A Possessive pointer OWNS an object.  'new' returns possessive pointers

var p:[N32]%;   // p is a possessive pointer to an array of N32's
[N32] 10 new p= //p now owns an array of N32's

Possessive pointers have some restrictions on them, intended to prevent leaks.
    - They must be stored or freed : If a function takes a possesive pointer as an argument, it MUST do something with it:
            -Assign it to a global or heap variable
            -Pass it on to another function to deal with
            -Free it
            -Return it to the callee
            If the program abandons the pointer (the variable goes out of scope), the pointer is automatically freed.

    - Writing to a possessive pointer variable will free anything that pointer is already pointing to
            [N32] 10 #myArray  //create array of 10
            [N32] 20 myArray=  //create array of 20.  Storing the pointer to this in myArray FREEs the previous value
   
    
Reference Pointers
    Reference pointers also have restrictions, intended to prevent pointers to local variables from being used outside their scope
    
        -   Reference pointers created in a function cannot be assigned to:
            - global variables, fields in structs or elements of arrays that are global or in the heap  //prevents local variables from escaping
            - cannot be assigned to variables in the same scope they are created. //prevents a pointer to an object from outliving the object. (However, creating the reference and then calling a function, during the duration of the function call, the caller HAD (and HAS) a pointer to the object... The object cannot be freed until at least the called function returns.

        -  Reference pointers can:
            -be offset/indexed by .structFieldName or arrayIndex[]
            -can be passed to functions
            -Reference pointers received as arguments (and values derived from them) can be stored in a local variable.
            
        -  Reference pointers cannot be returned from functions (prevent pointer to local variable from escaping)

    When a function recieves a reference pointer as an argument, the pointer is guaranteed valid for the entire function call, because it is either a refernence to an object in a higher stack frame, OR it is a  

Pointer demotion:

    When a possessive pointer variable is read onto the stack, it is demoted to a reference pointer.

        myArray                     //a reference pointer to the array
        myArray n[].structField&    //a reference pointer to the field

    To take a possessive pointer, the keyword 'take' is used:

        myArray take    //stack now contains a possessive pointer to myArray.  There is a catch:  myArray is now NULL... the stack has the only copy of the pointer

            This pointer to the array is a hot potato: it has to be passed around.  It can be written to another possessive variable.  It can be passed to a function.
            There is also the built-in trash which just frees it:

        myArray take #yourArray     //yourArray points to the array; myArray is now null
        yourArray take trash        //yourArray is NULL (because its taken), and trash frees it


    Another option is 'keep', which increases the reference count of an object:
        myArray keep #ourArray      //myArray and ourArray are the same array.  Two pointers to it
        
    You cannot keep or take offset pointers.   'myObject keep' is OK, but you cannot myObject .x& keep ... it doesn't make sense


    All objects created with 'new' use reference counting garbage collection.  The user is responsible for avoiding or breaking reference cycles.  Except for that, a program doesn't have to worry about leaking.  Reference counting was chosen because it is easy to implement and is fast.   In general, functions that want to read/write some structure should just use Reference pointers.  The only time a Possessive pointer should be passed to a function is if that function is going to store the pointer into some data structure or will free it.  Possesive pointers passed to functions can just be forgotten about.  Reference pointers received by a function as an argument don't need to be reference counted because 1) the caller holds a reference to the object, so it is impossible for the object to go out of scope in the current function 2)the pointer cannot be returned, or written to the heap; it will die when the scope of the current function ends, and is impossible to leak.
    
Procedures

A procedure is defined like this:

proc add:(a:Z32; b:Z32 -> Z32)
    a b + return
end

The general form is:

proc name:( argname:type; argname:type ... -> type)


end

Returning a value is optional:

proc addprint:(a:Z32;b:Z32->)
    a b + print
end

At most one value can be returned.

Procedures are simply called by name:

1 2 addprint    //prints 3

4 5 add #x      //stores 9 in x

The return keyword returns the top value on the stack.
In the case of a procedure that doesn't return a value, the return keyword simple returns from the function.

When a function returns any extra items on the stack are discarded... When a function returns if any local variables are non-null possessive pointers, they are freed.

Virtual data types:

The virtual keyword defines a virtual datatyps:

virtual Animal;

Virtual types can only be passed or stored by pointer:

var a:Animal%;  //a points to an animal


Virtual types can have be passed to functions;

proc NSpeak:(a:Animal&; b: Z32->)
    a #x
    loop a b < while
        a Speak     //call Speak
        a 1 + a =
    end
end

In this case NSpeak works on any Animal reference.

Speak could be defined in a generic way like NSpeak above:

proc Speak:(a:Animal& ->)
    "hello" print
end

But it could defined instead as a selector:

selector a Speak:(a:Animal&->);

A Selector isn't a function, but selects a function.  The 'a' after selector is naming arg a is the selecting argument... which function selected will depend on the real type of argument a.

Suppose we have two different data types, each with their own Speak function:

proc Speak:(c:Cat&->)
    "meow" print
end

proc Speak:(c:Dog&->)
    "woof" print
end

And each of these types declare to support Animal:

type Cat
    a:Animal;   // the 'a' field takes no space in a Cat type; it is an assertion the Cat can support the Animal type
end

type Dog
    a:Animal;
end

then:

Dog new #d
Cat new #c

d Speak //says woof
c Speak //says meow
c 10 NSpeak //says meow 10 times

The selector does not have to be the first argument, it can be any argument:


selector b SetName:(name:String%; b:Animal& ->);    

The above would require Cat, Dog or any other type implementing Animal to have a SetName procedure.  But what if we want all animals to have a Name field, and have setname be generic?
Then we use a data selector instead:

selector Animal.Name:String%;   //all Animal objects have a String% field Name.


type Cat
    a:Animal;   // the 'a' field takes no space in a Cat type; it just makes sure the Cat datatype creates an Animal selector table.
    someCatData:Z32;
    Name:String%;
end

type Dog
    a:Animal;
    Name:String%;   //note Name would be in a different offset in a Dog than Cat, because Cat has CatData and Dog doesn't.  That's ok.
end


proc SetName:(name:String%;a:Animal&->)
    name take a.Name=  //Stores the name string pointer in the Name field of any Animal object, no matter what its offset is.  The offset is stored in the object's type's selector table.
end


Casting:

A real type can be converted to any virtual type it implements:

d keep :Animal% #ad  // ad points to the same Dog as d, but as an Animal
c take :Animal% #ac  // ac points to the same Cat as c did , but as an Animal, and c is now null


A virtual type can be converted back to its real type:

ad:Dog&     //Animal& is turned back in to a Dog&
ad:Cat&     //Animal& is not a cat, so this evaluates to Null.

The way to check a cast is:

aa :Cat& ##c if     //attempt to cast to cat, storein c, keep on stack for the if statement
    c CatFunction       //do something only for cats
    "was a cat" print
else
    "not a cat" print
end


You could do an if/else chain if you really need to:

aa:Cat& ##c if
    //cat stuff on c
aa:Dog& ##d elseif
    //dog stuff on d
aa:Duck& ##du elseif
    //duck stuff on du
else
    //i don't know what it is
end

virtual Mammal;
virtual Bird;

type Cat

type Dog
    a:Animal;
    m:Mammal;

type Duck
    a:Animal;
    b:Bird;
    Name:String&; //for animal
end

A Dog or cat can be cast to either Mammal or Animal.

All Mammals are Animals, but as it is here you cannot cast a Mammal to an Animal.
But if a data selector is added:

selector Mammal.a:Animal;

Then every Mammal needs an Animal selector table.

m:Animal& is not possible, because every Mammal selector table has a pointer to an Animal selector table.

This allows overlapping interfaces:

virtual Reader;
selector r Read:(r:Reader&; dest:[N8]&; count:N32 -> N32);    //every reader has to Read

virtual Writer;
selector w Writer:(w:Writer&; src:[N8]& ; count:N32 -> N32);    //every writer has to Write


virtual ReadWriter;
selector ReadWriter.r:Reader;   //every ReadWriter has to be able to be a Reader
selector ReadWriter.w:Writer;   //every ReadWriter has to be able to be a Writer

type FileReader
    r:Reader;
end

type FileWriter
    w:Writer;
end

type FileReadWriter
    r:Reader;
    w:Writer;
    rw:ReaderWriter;
end

Now any function can take a ReaderWriter&, and through casts, either Read or Write as needed.


myRW:Reader& Read
myRW:Writer& Write


The same functions could also be made accessible directly by a readerwriter:
selector rw Read:(rw:ReaderWriter&; dest:[N8]&; count:N32 -> N32);   
selector rw Write:(rw:ReaderWriter&; src:[N8]&; count:N32 -> N32);   

mwRW myArray 10  Read
myRw myArray 10  Write

But if a function that has a ReaderWriter wants to call a function that accepts a Reader, it can still do so:

myRw:Reader& SuperReadFunction  //SuperReadFunction takes a Reader&

In short with virtual types:

    Can create polymorphic functions with different behavior according to the real type.
    Can real types to virtual and back.
    Can require virtual types support other virtual types.
    Can require implementors of Virtual types to contain specific fields.
    
    
For instance:
virtual LinkedList;
selector LinkedList.Next:LinkedList%;

Any data structure that needs to be in a linked list can just do this:
type ListOfCats
    //all kinds of kitty stuff
    list:LinkedList;    //ListOfCats implements LinkedList
    Next:LinkedList%;   //Needs a Next field, to another LinkedList
end
    
The above is not perfect... list of cats could have non-cat LinkedList elements in it.
